# Развёртывание на VPS

Проект живёт на сервере в Амстердаме и публикует посты сам, дважды в сутки. Участие не требуется.

## Что где

| Что | Где |
|---|---|
| Код | `/opt/motivation` |
| Виртуальное окружение | `/opt/motivation/venv` |
| Токены | `/opt/motivation/.env`, права 600 |
| Журнал публикаций | `/opt/motivation/post_log.json` |
| Лог запусков | `/opt/motivation/autopost.log` |
| Вывод cron | `/opt/motivation/cron.log` |
| Расписание | `/etc/cron.d/motivation` |

Картинки уходят в репозиторий `nika-media`, папка `motivation/`. Локальная копия удаляется сразу после успешной публикации, поэтому `output/` всегда пуст.

## Расписание

Файл лежит в репозитории — `deploy/motivation.cron`, и ставится копированием:

```
cp /opt/motivation/deploy/motivation.cron /etc/cron.d/motivation
chmod 644 /etc/cron.d/motivation
systemctl restart cron
```

Активные строки:

```
0 3  * * * root cd /opt/motivation/tools && nice -n 15 ionice -c3 ../venv/bin/python autopost.py
0 15 * * * root cd /opt/motivation/tools && nice -n 15 ionice -c3 ../venv/bin/python autopost.py
```

**Про часовой пояс — здесь легко ошибиться.** Системное время сервера UTC, и менять его нельзя: на машине работает VPN, трогать общесистемные настройки ради расписания незачем.

Первая версия полагалась на `CRON_TZ=Europe/Moscow`, и это **не сработало**: строка молча игнорируется, задача уходила по UTC, а посты выходили в 09:00 и 21:00 вместо 06:00 и 18:00. Обнаружилось только через сутки, по времени в ленте.

Причина: `CRON_TZ` — расширение cronie из Red Hat, а в Debian и Ubuntu стоит vixie-cron, который такой переменной не знает. Ошибки при этом нет, задача просто работает по системному времени.

Поэтому время задано прямо в UTC: **03:00 UTC = 06:00 МСК**, **15:00 UTC = 18:00 МСК**. Пересчёт безопасен навсегда — Москва с 2014 года стоит на UTC+3 и на летнее время не переходит.

Проверить, когда задача сработала на самом деле:

```
journalctl -u cron --since today | grep motivation
```

Это системное время, то есть UTC. В `cron.log` то же событие записано по Москве — скрипт считает время сам.

**Про nice и ionice.** Запуск идёт с пониженным приоритетом по процессору (`nice -n 15`) и по диску (`ionice -c3`). При любой конкуренции за ресурсы публикация уступит дорогу VPN. По факту это перестраховка: замер во время работы показал load average 0.06 и ни одного лишнего мегабайта памяти.

## Соседство с VPN

На сервере работает **wg-easy** (WireGuard в Docker), занимает около 140 МБ. Публикация добавляет к этому нагрузку, которую не видно в статистике: два запуска в сутки по 12 секунд.

Замеры до и после установки:

| | До | После |
|---|---|---|
| Память занято | 295 МБ | 296 МБ |
| Load average | 0.02 | 0.06 |
| Свободно на диске | 19 ГБ | 18 ГБ |

## Обновление кода

```
cd /opt/motivation
git pull
```

`.env`, журнал и логи в репозитории не хранятся, поэтому `git pull` их не затрагивает.

Если менялись зависимости:

```
./venv/bin/pip install -r requirements.txt
```

## Проверка

Посмотреть, что уйдёт, ничего не отправляя:

```
cd /opt/motivation/tools
../venv/bin/python autopost.py --dry-run
```

Опубликовать вручную, не дожидаясь расписания:

```
cd /opt/motivation/tools
../venv/bin/python autopost.py --slot=6
```

Статистика базы цитат:

```
cd /opt/motivation/tools
../venv/bin/python add_quotes.py --stats
```

## Если что-то пошло не так

**Смотреть `autopost.log`** — там причина каждого запуска: не наступил слот, лимит выбран, сеть недоступна, ошибка публикации.

**`cron.log`** — если задача вообще не запускалась, ошибка будет здесь.

**Проверить, жив ли cron:** `systemctl is-active cron`

**Токен Instagram живёт 60 дней.** Когда истечёт, публикация начнёт падать с ошибкой доступа. Перевыпуск — по инструкции в `docs/instagram-checklist.md`, затем поправить `IG_ACCESS_TOKEN` в `/opt/motivation/.env`.

## Защита от повторов

Три уровня, потому что cron может сработать дважды при перезапуске сервера или сдвиге времени:

1. **Флаг `used` у цитаты** — использованная не берётся заново
2. **Журнал `post_log.json`** — хранит, какой слот какого дня уже отработан
3. **Файл блокировки** — не даёт двум запускам работать одновременно, снимается сам через 15 минут

Чередование фона считается по сквозному счётчику публикаций из журнала, а не по часу. Так порядок белый — чёрный — белый — чёрный сохраняется при любом расписании и не сбивается после пропуска.

## Переход на четыре поста

Когда аккаунт устоится, в `/opt/motivation/.env` поменять:

```
SLOTS=0,6,12,18
```

И добавить две строки в `deploy/motivation.cron` — **21:00 и 09:00 UTC**, это полночь и полдень по Москве. Дальше скопировать файл в `/etc/cron.d/` и перезапустить cron.
